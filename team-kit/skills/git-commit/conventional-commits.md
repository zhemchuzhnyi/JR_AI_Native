# Conventional Commits

Краткая памятка по формату сообщений Git-коммитов. Conventional Commits задаёт единый способ описывать назначение изменений в истории проекта.

## Формат сообщения

```text
<тип>[необязательная область]: <краткое описание>

[необязательное подробное описание]

[необязательный нижний колонтитул]
```

Примеры:

```text
feat(auth): добавить вход по одноразовому коду
fix: исправить обработку пустого ответа
```

- **Тип** обязателен и указывает характер изменения.
- **Область** необязательна: название компонента или части проекта в круглых скобках.
- После двоеточия и пробела указывается краткое описание.
- Подробное описание и нижние колонтитулы отделяются от заголовка пустой строкой.

## Распространённые типы

| Тип | Назначение |
|---|---|
| `feat` | Новая функциональность |
| `fix` | Исправление ошибки |
| `docs` | Изменения документации |
| `style` | Изменения форматирования, не влияющие на логику (например, пробелы или точка с запятой) |
| `refactor` | Изменение кода без исправления ошибки и без добавления функциональности |
| `perf` | Улучшение производительности |
| `test` | Добавление или изменение тестов |
| `build` | Изменения системы сборки или внешних зависимостей |
| `ci` | Изменения конфигурации и сценариев CI |
| `chore` | Прочие технические задачи, не меняющие поведение продукта |
| `revert` | Отмена ранее внесённого коммита |

Типы, кроме `feat` и `fix`, не являются обязательным закрытым списком: проект может договориться о дополнительных типах.

## Несовместимые изменения

Несовместимое изменение можно отметить одним из двух способов:

1. Добавить `!` после типа или области:

   ```text
   feat(api)!: удалить поддержку версии v1
   ```

2. Добавить нижний колонтитул `BREAKING CHANGE:` с описанием последствий:

   ```text
   refactor(api): изменить формат ответа

   BREAKING CHANGE: поле `user_name` переименовано в `username`.
   ```

Можно использовать оба способа одновременно. `BREAKING CHANGE` пишется заглавными буквами; описание должно объяснять, что именно изменилось и что нужно сделать пользователям.

## Нижние колонтитулы

Нижние колонтитулы добавляют ссылки на задачи и другую метаинформацию. Например:

```text
fix(parser): корректно обрабатывать пустой ввод

Closes #42
Reviewed-by: Имя Фамилия
```

Каждый колонтитул записывается в отдельной строке. Синтаксис и назначение таких строк зависят от правил проекта и используемых инструментов.

## Рекомендации

- Пишите кратко и конкретно: укажите, что изменилось.
- Используйте одну тему на коммит; несвязанные изменения разделяйте.
- Не выбирайте `feat` или `fix` только ради важности задачи: тип должен отражать реальные изменения.
- Если область помогает понять, какую часть проекта затронули, укажите её, например `docs`, `auth` или `api`.
- В подробном описании объясняйте мотивацию и важные детали, а не повторяйте заголовок.
- Указывайте `BREAKING CHANGE`, если изменение несовместимо с предыдущим поведением или интерфейсом.

## Примеры

```text
docs: добавить инструкцию по запуску

test(api): покрыть проверку авторизации

fix(cli): показать понятную ошибку при неверном аргументе

feat!: удалить устаревший формат конфигурации

build(deps): обновить версию pytest
```
